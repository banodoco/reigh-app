**Shared metaplan:** [Reigh Cloud — coordinated projects and execution schedule](/Users/peteromalley/Documents/reigh-workspace/reigh-app/docs/design/cloud-mode-megado-projects-2026-10-05.md).

**Purpose.** This document lists what is already settled by the Local/Cloud direction, what source code can be reused, what must be adapted or added, and which bounded prototypes close the remaining engineering decisions. It complements [Cloud mode integration plan](cloud-mode-integration-plan-2026-10-05.md); it does not claim implementation or live-service verification. The detailed source ledgers are linked below. ## Current user decisions (2026-10-05)

The first customer-facing agent model is DeepSeek API `deepseek-flash` (DeepSeek-V4.1-Flash) at `https://api.deepseek.com`; record the mutable alias's actual returned model/date and verify OMP tool calling, streaming, and usage compatibility. This does not change Megado worker/run model configurations. Terminal task success, failure, or cancellation must publish a durable Runtime completion event and automatically continue the originating agent plan once. Project 03 owns durable task completion/outbox identity; 04 owns controller inbox delivery, native session notification and follow-on turn; 06 owns waiting/resuming UI and joined proof. Delivery is deduplicated and durably acknowledged after the native OMP write/flush, queues behind an active turn or native writer, and resumes from committed state with a fresh grant/current writer. It respects cancellation, stale leases, account disable/revocation, and does not retry failed work or replay the old LLM turn. The accepted 24-hour paused-sandbox retention removes scratch after durable Runtime/BlobStore state is confirmed, not Turso history; a later task result may recreate a sandbox and continue.

Cloud charging uses simple measured usage through one prepaid balance for model inference, allocated active-sandbox time, generation, and rendering. Reserve an estimate, settle verified actual usage once, and release unused hold. Proposed initial tariff for product confirmation: 1× measured underlying cost and 0% markup. Completed provider work is recommended to incur measured usage even if its output is disliked; duplicate or infrastructure-fault charges are not passed through. Markup/rounding and the narrow failed/cancelled/ambiguous-cost tariff remain product decisions. No arbitrary daily-spend, conversation/concurrency, or LLM-budget quotas are planned. Atomic balance reservation, provider-imposed limits, scoped authorization, idempotency, one writer per conversation, and operator emergency stop remain technical safeguards.

## Clean replacement policy

**User decision:** replace obsolete execution architecture aggressively. The cloud orchestrator has one supported task contract and one execution path. Port useful provider request/poll/download logic into that path, then remove the old queue consumer, legacy task payload handling, startup status resets, old completion/billing calls, compatibility shims, fallback switches and their obsolete tests/configuration. Do not maintain parallel orchestrator versions. Provider-specific handlers implementing the new contract are ordinary implementation code, not legacy compatibility adapters.

Cutover must account for already-running work and preserve required historical account, payment and task records. Drain or explicitly reconcile old in-flight jobs, switch deployment, and remove the obsolete runtime paths. Historical data and applied migration history are not a reason to retain old executable behavior; retiring tables must first resolve their ledger references. This is the implementation direction, not authorization to erase financial history or evidence that any deletion has already occurred.

## Hosted-agent usage and lifecycle contract

Use one prepaid balance for model inference, allocated active-sandbox time, generation, and rendering. Reserve an estimated amount before work; settle verified actual usage once and release unused hold. Charge completed provider work at measured usage even when the user dislikes the result; do not silently pass through duplicate or infrastructure-fault charges. Markup and failed/cancelled/ambiguous-cost treatment still need a narrow tariff decision. Use the account and conversation as attribution dimensions,

For the first sandbox prototype, prepare a pinned E2B template and benchmark 2 vCPU/4 GiB; consider 1/1 only after real OMP and skill memory/reliability proof. The controller starts/resumes on admitted turn, keeps the sandbox during active work, then provisionally pauses after 90 seconds idle at a committed turn/tool boundary. Browser disconnect and network timeout are not idle/cancel signals. The controller owns the idle timer, provider lifecycle epoch, grant refresh, ACP reconnect/replay and lost-ack reconciliation. Resume must mint a fresh scoped grant and reject the former writer generation. Background task execution uses its own Runtime lease and must neither require nor prolong the chat sandbox.

## Astrid Cloud profile and command routing (proposed, not implemented)

Astrid’s product commands already converge on the public `AstridClient`/`RemoteAstridClient` facade: the CLI dispatch layer opens a client and passes it to family commands (`astrid/core/gateway/dispatch.py:297-304,374-377`; OMP is a separately versioned external dependency in `/Users/peteromalley/Documents/oh-my-pi` at inspected HEAD `c73e346643` and must be pinned with the hosted image, not inferred from Astrid source SHA), while `AstridClient.open()` validates explicit endpoint, credential, realm/actor and protocol, then builds a `WorkspaceClient` and `RemoteAstridClient` (`astrid/sdk/client.py:152-235`). That is a credible same-command Cloud transport seam. It does not mean an existing Cloud profile switch exists: `open_from_launcher()` currently calls `ensure_runtime()` and launches/resolves the local Runtime (`client.py:237-298`), and CLI commands use that launcher. Cloud mode therefore needs an explicit profile resolver/launcher branch; merely setting a browser Local/Cloud toggle will not redirect Astrid commands.

Proposed UX/API (new, illustrative): `astrid profile login --provider supabase`, `astrid profile set cloud`, `astrid profile status`, and `astrid profile set local`; corresponding API could be `AstridClient.open_from_profile(profile="cloud")`. Store Supabase refresh/session material in OS credential storage, never Turso URL or DB credentials. On command startup the Cloud resolver obtains/refreshes the user’s Supabase session, calls an authenticated Reigh Cloud Gateway for an opaque short-lived Runtime grant plus endpoint/realm/actor/protocol, then calls the existing explicit `AstridClient.open(endpoint=..., credential=..., realm_id=..., actor_id=..., ...)`. Gateway maps the signed-in user to their server-owned Turso DB; the SDK never connects to Turso directly. The Local profile keeps the current `ensure_runtime()` and loopback validation untouched. A hosted agent receives only a short-lived scoped operation grant/tool broker, not the CLI user’s refresh token or Runtime master credential; it uses the same typed SDK facade through that broker/gateway. Preserve current HC-04 task admission and Runtime result APIs; Supabase dispatch is separate execution-job transport, and only the agent may submit tasks in the first slice.

Cloud mode makes canonical projects, tasks, events, generations, object identities and media bytes persistent remotely through Runtime/Turso/BlobStore. It does not eliminate all local files: packs that render, transcode or call tools requiring paths still need sandbox-local temporary inputs/output. For example `astrid/sdk/remote.py:113-121` materializes VibeComfy objects under a temporary directory; `Astrid/packs/fal/executors/h3_video/run.py:55-74,126-149` stages prompts/references as files; `Astrid/packs/vibecomfy/src/dimensional_ltx.py:152-173` deliberately carries CAS object IDs rather than paths at its typed boundary. Cloud adapters should download authorized inputs to per-job sandbox scratch and upload/finalize outputs through BlobStore before Runtime publication. Scratch is ephemeral; it is not the project’s persistent authority. Commands whose explicit contract imports/exports arbitrary filesystem paths remain local I/O workflows until a Cloud-aware upload/download path is specified.

### Universal Astrid conversation persistence (proposed; not implemented)

Chat records should persist whenever the actual Astrid agent is used, including standalone Astrid CLI/TUI/ACP and Reigh. Data authority is independent of compute location: desktop Astrid and hosted Astrid may both select the same Cloud profile; Local selects local SQLite/CAS. One per-user DB contains many conversations. Put shared conversation identity and lifecycle in Astrid Runtime, not only the Reigh browser bridge: local uses Runtime SQLite+CAS; Cloud uses the signed-in user’s Turso realm+private BlobStore. Use stable `conversation_id` and OMP `session_id`; keep optional `project_id` because a standalone chat may have no project. Runtime owns APIs/schema for user-turn intent/ack, durable ordered event cursor and UI display projection, plus a per-conversation active-writer lease and stable turn ID. This prevents desktop and hosted clients from producing divergent concurrent OMP histories. OMP's native session JSONL/history remains the resume authority; use its existing `SessionStorage` seam rather than inventing a transcript archive/reconstruction format. OMP source at `/Users/peteromalley/Documents/oh-my-pi` HEAD `c73e346643` has `SessionManager.create(..., storage)` (`packages/coding-agent/src/session/session-manager.ts:2626`), `open(..., storage)` (`:2713`), an indexed storage protocol (`packages/coding-agent/src/session/indexed-session-storage.ts`), and a Redis backend precedent (`redis-session-storage.ts:9-43,91-109+`). Wire a Runtime-backed SessionStorage implementation into the common branded CLI/TUI/ACP initialization; no such wiring was found. Runtime should own the session adapter/API and persist OMP native structured session records, indexes and event cursor in its DB; the inspected indexed storage interface is `readFull`, `readSlices`, `writeFull`, `append`, `updateSessionTitle`, `truncate`, `remove`, and `move`. Implement these atomically with session version/writer lease and drain/flush semantics. Turso/SQLite is the session store; BlobStore is for attachments/large artifacts and optional checkpoint bundles, not a required archive of all session state. Raw structured messages/tool results remain queryable and UI projection is read-only, not a second editable transcript. Verify `message_end` listener persistence hook (`agent-session.ts:3739-3754`), flush/drain ordering and reconnect/replay. Any extra non-secret profile artifacts may be allowlisted managed objects; never archive HOME/profile or auth/token/API credential files; inject fresh scoped credentials on restore. OMP connects only through an Astrid session adapter/API; it never opens SQLite or Turso directly. Persist raw structured ACP/OMP message and tool-call/result events, not only rendered text. Persist native session records continuously through Runtime; after each completed turn, flush OMP storage and atomically record the event cursor/turn acknowledgement before the client reports completion. A process loss must reopen the same native JSONL session from its versioned managed-object index; test partial append and duplicate event delivery. Supabase stores thin operational records only: current sandbox ID/placement, lease, scoped grant and lifecycle status; a sandbox ID may change while conversation/session IDs remain stable. Controller resolves user→realm via Supabase, asks Runtime for the conversation/checkpoint, provisions an isolated sandbox, restores OMP state, and tails durable Runtime events. Job results remain in Runtime/object storage and link to the conversation turn, so they survive sandbox termination. On checkpoint upload followed by failed pointer commit, reconcile/delete the orphan; after destruction, restore the same OMP session and resume event cursor. Current code only proves Reigh-specific project/session association and in-memory browser queues, not this standalone/persistent contract; implementation must wire the existing OMP SessionStorage seam into common branded CLI/TUI/ACP startup through an Astrid session adapter and Runtime API. Make this a dedicated Astrid + OMP work package: OMP SessionStorage ↔ Astrid adapter ↔ Runtime API ↔ SQLite/Turso+BlobStore. Acceptance requires standalone Astrid and hosted ACP reopening the same conversation/session ID, reading the same native structured JSONL history, and serializing turns through one Runtime writer lease; hard-kill during append/truncate/fork, reopen the same DB-backed session and replay from a durable event cursor without duplicate/lost events; prove OMP session methods do not require a full blob snapshot for every turn. Chunk/layout choice remains a prototype gate.

## Contracts the implementation spec must freeze

1. **Mode and identity:** persisted mode scope (recommend per-device/profile; the Cloud realm remains account-owned, and switching one device must not redirect another device’s work); auth principal; server-derived authenticated-user/project/realm mapping; one operation uses one authority. Current Local URL validator remains loopback-only; introduce a separate TLS/origin-allowlisted Cloud HTTPS profile rather than relaxing the local validator globally. Switch affects future work only. No sync, fallback mutation, or browser-selected Turso URL. On account/workspace/mode change, dispose provider subscriptions and key caches by mode/account/workspace/realm.
2. **Agent capability grant:** random opaque short-lived per-session grant, hash-only at rest, revocable; binds Supabase subject, workspace, project, conversation/session, allowed read/edit/task operations, exact capability/model/mode/count, expiry, request quotas and the currently approved spend limit (none is invented here). Edge Function either validates a Supabase JWT at gateway or disables `verify_jwt` and validates every opaque token itself. It derives owner/scope from server lookup. Never pass service-role, Turso, provider, worker or Runtime master credentials to agent. Input-media links are short-lived and project scoped.
3. **Task intent/response:** stable tool intent ID remains same across ACK loss, grant rotation and conversation resume; bind canonicalized request digest so same key/different body conflicts. Agent can submit only allowlisted HC-04 typed capability. API returns 202 + Runtime task ID/status/result links after durable admission/outbox (or distinct submission ID if admission is asynchronous). Status/result/cancel each re-authorize scope. Result is managed Runtime object refs, not provider URL as authority. UI and agent can both read after sandbox exit.
4. **Claim/dispatch ordering constraint:** existing Runtime claim chooses the next eligible task for `(executor_id, capability_ids, runtime_epoch)` and does **not** accept `task_id` selector (`service.py:5866-5929`; route `server.py:579-587`). Do not specify a nonexistent exact-task claim. Minimal beta design: serialize the dispatcher per realm; Runtime owns admitted task+outbox; dispatcher claims through current API, then matches the returned task/attempt to its outbox intent, and in one Supabase RPC creates the exact-price hold plus the delivery row for that returned attempt. The transaction commit makes the held row worker-visible; workers cannot observe a delivery without its hold. If no funds, no provider call; fail/cancel/reconcile that exact claimed attempt and do not bill another queued task. Add a two-same-capability-task/out-of-order-return regression to prove the owner, quote and envelope bind to the actual task returned, and replaying claim idempotency does not consume the next task. Do not add targeted claim unless this fixture proves claim-first is unworkable. Supabase delivery lease is transport only; Runtime lease/fence is execution authority.
5. **Provider uncertainty and result:** Worker records stable provider idempotency/request ID before polling when supported. Crash/timeout after provider submit must reconcile status; unknown outcome stays explicit and cannot blind-resubmit or release hold while spend may be active. Output locator + SHA-256 + size + MIME are untrusted until trusted Runtime bridge retrieves/verifies bytes, finalizes BlobStore and settles current task/attempt/fence. Stale/cancelled/wrong-project output is rejected. Runtime emits a billing-result outbox; Supabase settlement/release retries idempotently without reverting Runtime success.
6. **Task usage reservation, metering and user charge policy:** Source indicates Stripe/grant balances are cents and final columns support fractional cents (`numeric(10,3)`), but task price/calculation units need reconciliation. Use an estimated-usage hold before dispatch and settle verified actual task/provider usage through the single prepaid balance; retain separate, idempotent model-request and allocated-sandbox metering. Normalize token categories to avoid double-counting overlapping input/output/cache/reasoning totals and record allocated vCPU/RAM elapsed seconds, not sampled CPU utilization. Selected customer-agent route is DeepSeek API `deepseek-flash`; record actual returned model/date and verify OMP tool-call, streaming, and usage compatibility ([official API model/pricing docs](https://api-docs.deepseek.com/quick_start/pricing)). Proposed initial tariff is 1× measured underlying cost and 0% markup, pending product confirmation; failed/cancelled/ambiguous-cost treatment remains open. No arbitrary user budget/concurrency caps. Reconcile delayed usage and controller restart/lost pause acknowledgement idempotently without implying this halts provider billing already accrued.
7. **Runtime/Turso/BlobStore:** one user realm owner; authenticated gateway maps Supabase JWT plus the authenticated user’s project scope to that user’s realm and holds Turso credentials. Existing protocol `/v1/tasks`, `/claim`, `/attempts/*` semantics remain. Driver must preserve DDL/migrations, transactions/savepoints, idempotency, CAS, event sequencing, lease fencing, restart epoch and one-writer assumptions. Blob upload is pending→uploaded→verified→metadata-published; object bytes upload before metadata association. Reconcile orphan bytes; do not publish missing/unverified objects. TUS path for >6 MiB and test configured bucket cap; never funnel large bytes through Edge Function.
8. **OMP durability/security:** ACP event delivery gets ordered durable cursor/replay; browser's in-memory draining event queue is not persistence. OMP canonical session ID/profile must resume after host hard destruction, not only E2B pause. Astrid CLI-driven skills may require shell; prefer a custom tool-only profile if supported, otherwise keep CLI inside a hardened sandbox with no ambient secrets and require server-enforced operation/project/capability authorization plus egress controls. Prompt restrictions are not tenant isolation. Pin image, Astrid/OMP build and skill/model catalog digest; track SBOM and redistribution entitlement.
